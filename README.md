# Proejct1 — sbomfuzz

**sbomfuzz** проводит фаззинг-тестирование компонентов из SBOM. Обёртки пишет Claude, фаззит программа.
Вы передаёте SBOM в формате CycloneDX, и для каждого компонента выполняются шаги:

1. **Загрузка.** Компонент скачивается нужной версии: из PyPI, из Maven Central или исходники C/C++.
2. **Обёртки.** Claude по вашей подписке (через Claude Code) изучает API и пишет до 3 фаззинг-обёрток,
   к каждой ровно 3 стартовых входа.
3. **Проверка.** Программа собирает каждую обёртку и прогоняет на ней её входы. Если что-то не так,
   ошибки уходят Claude на исправление. По умолчанию даётся 3 попытки, обёртки, не прошедшие проверку,
   отбрасываются.
4. **Фаззинг.** Программа без участия Claude фаззит каждую принятую обёртку заданное время: Atheris для
   Python, Jazzer для Java, libFuzzer с ASan/UBSan для C/C++. После падения фаззер перезапускается и ищет
   дальше всё заданное время. Одинаковые падения склеиваются по типу ошибки и месту, в том числе
   найденные разными обёртками; лишние файлы повторов не сохраняются.
5. **Отчёт.** `report.md` и `report.json` содержат сырые находки: тип ошибки, стек, файл входа и команду
   воспроизведения. Оценки серьёзности и разбора нет: часть падений может быть ошибкой самой обёртки.
   Jazzer кроме падений сообщает находки своих детекторов (`FuzzerSecurityIssue*`: инъекции в регулярные
   выражения, десериализация и т. п.). Иногда это штатная возможность библиотеки: например, CSS-селекторы
   jsoup по документации принимают регулярные выражения.

| Экосистема | purl | Фаззер | Откуда берётся код |
|---|---|---|---|
| Python | `pkg:pypi/...` | Atheris | `pip install` нужной версии с зависимостями |
| Java | `pkg:maven/...` | Jazzer | Maven Central: jar, зависимости, sources jar |
| C/C++ | `pkg:github/...`, `pkg:generic/...`, `pkg:conan/...` | libFuzzer + ASan/UBSan | архив по `download_url` или external reference `distribution`, либо `git clone` по `vcs_url` |

Компоненты других экосистем (npm, Go и т. д.) попадают в отчёт со статусом `skipped`.

## Как начать

```bash
git clone https://github.com/godbleeesd/Proejct1.git
cd Proejct1
docker build -t sbomfuzz .
```

Посмотреть, какие компоненты SBOM можно фаззить (вход в Claude не нужен):

```bash
docker run --rm -v "$PWD:/data" sbomfuzz list examples/sample-bom.json
```

### Токен подписки Claude (Pro, Max, Team, Enterprise)

Создайте токен один раз. Claude Code уже есть внутри образа:

```bash
docker run -it --rm --entrypoint claude sbomfuzz setup-token
```

Откройте ссылку из терминала в браузере, подтвердите вход и вставьте полученный код. Токен действует год,
храните его как пароль.

### Запуск

```bash
docker run --rm -e CLAUDE_CODE_OAUTH_TOKEN -v "$PWD:/data" sbomfuzz run examples/sample-bom.json --out results
```

Отчёт появится в `results/report.md`. В `results/` также лежат:
- `plan.json` — какие компоненты обработаны и какие пропущены;
- `bundles/<компонент>/` — комплект от Claude: `bundle.json`, обёртки, скрипт сборки и стартовые входы
  (в `workspace/`), журнал работы Claude;
- `fuzz/<компонент>/<обёртка>/` — результат фаззинга: `result.json` и входные данные падений (`crashes/`).

Лимиты подписки тратятся только на этап с обёртками, фаззинг их не расходует. Если лимит закончится,
оставшиеся компоненты получат статус `usage_limit`, а отчёт по уже проверенным сохранится.

Как держать расход под контролем:
- **Кэш комплектов** (`--cache DIR`). Обёртки для `компонент@версия` пишутся один раз и сохраняются в кэш. В следующих
  запусках программа берёт их оттуда, проверяет на свежей загрузке компонента и, если проверка прошла, не вызывает
  Claude вообще. Если обёртки перестали работать, Claude пишет новые, и они заменяют старые в кэше.
  `--refresh-cache` принудительно пишет обёртки заново.
- **Потолок на сессию** (`--max-budget-usd`, по умолчанию 0.50). Сессия Claude останавливается, когда оценка её
  расхода достигает предела; обёртки, прошедшие проверку к этому моменту, фаззятся.
- **Уровень рассуждений и модель** (`--effort medium`, `--model …`): меньше размышлений — меньше токенов.

## Этапы для CI/CD

`run` выполняет все этапы фаззинга подряд на одной машине. В CI/CD каждый этап запускается отдельной
задачей, а результаты передаются между задачами как артефакты:

| Этап | Команда | Вход | Выход |
|---|---|---|---|
| 1. План | `sbomfuzz plan bom.json -o plan.json` | SBOM | `plan.json`: компоненты (по одной задаче на каждый) и пропущенные |
| 2. Обёртки | `sbomfuzz generate plan.json --slug <компонент> -o bundles` | план | `bundles/<компонент>/`: проверенные обёртки и входы |
| 3. Фаззинг | `sbomfuzz fuzz bundles/<компонент> [--harness <имя>] -o fuzz-results` | комплект | `fuzz-results/<компонент>/<обёртка>/` |
| 4. Отчёт | `sbomfuzz report plan.json --bundles bundles --fuzz fuzz-results -o fuzz-report` | всё выше | `report.md`, `report.json` |
| Статика | `sbomfuzz svace bom.json -o svace-results` | SBOM | архивы `svace-dir.tar.gz` и журналы сборки |

Этап фаззинга не зависит от машины, на которой писались обёртки: он заново скачивает компонент, восстанавливает
из комплекта обёртки и входы и собирает их. Поэтому обёртки одного компонента можно фаззить параллельно,
каждую в своей задаче (`--harness`). Если какого-то этапа не было, отчёт показывает это статусом компонента:
`missing` (нет комплекта) или `not_fuzzed` (нет результатов фаззинга).

## GitLab CI

Готовый пайплайн — [.gitlab-ci.yml](.gitlab-ci.yml). Он выдаёт два результата: статику и фаззинг.

```
build-image ──► plan ──┬──► svace ───────────────────────► svace-results/   (результат 1: статика)
                       │
                       └──► fuzzing (дочерний пайплайн)
                              generate:<компонент>  🤖 Claude пишет обёртки, по задаче на компонент
                              fuzz:<компонент> 1/3, 2/3, 3/3   по задаче на обёртку, параллельно
                              report ────────────────────► fuzz-report/      (результат 2: фаззинг)
```

Задача `plan` сама генерирует дочерний пайплайн (`sbomfuzz plan --gitlab-ci child-pipeline.yml`), поэтому число
задач подстраивается под SBOM.

Что настроить в проекте GitLab:
1. **Переменная `CLAUDE_CODE_OAUTH_TOKEN`** (Settings → CI/CD → Variables): токен подписки, Masked и Protected.
   Защищённые переменные доступны только в защищённых ветках, поэтому запускайте пайплайн из них.
2. **Runner для Svace** с тегом `svace`, у которого дистрибутив Svace смонтирован в `/opt/svace`
   (в `config.toml` раннера: `volumes = ["/путь/к/svace:/opt/svace:ro"]`). Без Svace поставьте `SVACE_ENABLED: "false"`.
3. **Runner с Docker-in-Docker** (privileged) для задачи `build-image`, которая собирает образ в реестр проекта.
   Она запускается при `git push`, меняющем код, или при любом запуске с `BUILD_IMAGE=true`.

Свой SBOM: положите файл в репозиторий и укажите его в переменной `SBOM`, либо при ручном запуске
(CI/CD → Run pipeline) передайте переменную `SBOM` типа File.

Обёртки кэшируются между запусками пайплайна (GitLab cache задач `generate`, ключ — компонент с версией): Claude
пишет обёртки для каждой версии компонента один раз. Кэш хранится на runner'е; чтобы он был общим для нескольких
runner'ов, в GitLab Runner настраивается распределённый кэш (S3 или MinIO). Написать обёртки заново:
`GENERATE_ARGS: --refresh-cache`.

Основные переменные пайплайна: `FUZZ_SECONDS` (время фаззинга одной обёртки), `MAX_HARNESSES` (обёрток на компонент,
это же число параллельных задач фаззинга), а также дополнительные аргументы этапов `PLAN_ARGS`, `GENERATE_ARGS`,
`FUZZ_ARGS`, `REPORT_ARGS` и `SVACE_ARGS`. Например, `REPORT_ARGS: --fail-on-crash` роняет пайплайн при найденном падении.

Коды выхода: `generate` — 5, если лимит подписки закончился (задачу стоит повторить позже); `report` и `run`
с `--fail-on-crash` — 3, если найдено падение; `svace` — 4, если компонент не собрался.

## Основные параметры `run`

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `-o, --out` | `sbomfuzz-results` | куда писать отчёт и артефакты |
| `-e, --ecosystem` | все | только `python`, `java` или `native` (можно повторять) |
| `-c, --component` | все | glob по имени или purl, например `-c 'pkg:pypi/*'` |
| `--limit` | — | обработать не больше N компонентов |
| `-j, --jobs` | 1 | сколько компонентов обрабатывать параллельно |
| `--fuzz-seconds` | 600 | время фаззинга на одну обёртку |
| `--stop-after-duplicates` | 0 | остановить фаззинг обёртки раньше, если N перезапусков подряд дали только известные падения (0 — всегда фаззить всё время) |
| `--max-harnesses` | 3 | обёрток на компонент |
| `--fix-attempts` | 3 | сколько раз Claude может исправлять обёртки после проверки |
| `--max-turns` | 40 | лимит шагов Claude на компонент |
| `--model` | модель вашего плана | модель Claude, например `claude-opus-5-5` |
| `--effort` | `high` | глубина рассуждений: `low` … `max` |
| `--language` | `English` | язык описаний обёрток, например `Russian` |
| `--max-budget-usd` | 0.50 | потолок расхода одной сессии Claude (оценка в пересчёте на API); обёртки, прошедшие проверку до остановки, сохраняются; 0 — без потолка |
| `--cache` | — | кэш комплектов: папка, где хранятся обёртки по версиям компонентов |
| `--refresh-cache` | выкл. | не брать обёртки из кэша, написать заново и заменить |
| `--fail-on-crash` | выкл. | вернуть код 3, если найдено хоть одно падение (для CI/CD) |
| `--keep-workdirs` | выкл. | не удалять скачанный код и сборки (нужно, чтобы воспроизводить падения) |

Полный список: `docker run --rm sbomfuzz run --help`.

## Воспроизведение падения

Для каждого падения в отчёте есть команда, например `PYTHONPATH=site python3 harnesses/fuzz_loads.py crashes/crash-…`.
Её нужно выполнять в рабочей папке компонента, поэтому запускайте с `--keep-workdirs` и `--workdir`,
смонтированным на диск, например `--workdir /data/work`.

## Статический анализ: сборка под Svace

Команда `sbomfuzz svace` — этап статического анализа. Для каждого компонента она скачивает исходники
и выполняет контролируемую сборку под Svace (`svace build`). Результат каждого компонента — архив
`svace-dir.tar.gz` с проектом Svace (`<проект>/.svace-dir`), он подаётся на `svace analyze`.

| Экосистема | Что собирается |
|---|---|
| C/C++ | исходники, система сборки определяется автоматически: CMake, Meson, autotools или Makefile. Шаг configure идёт вне Svace, чтобы его пробные компиляции не попали в анализ |
| Java | sources jar артефакта, компиляция `javac` с зависимостями из POM |
| Python | собственные модули пакета, без зависимостей (`svace build --python`) |

Svace не входит в образ: он лицензируется ИСП РАН. Смонтируйте дистрибутив (x64 Linux) в `/opt/svace`:

```bash
docker run --rm -v "$PWD:/data" -v /path/to/svace:/opt/svace sbomfuzz svace examples/test-bom.json --out svace-results
```

Результаты лежат в `svace-results/`: `report.md`, `report.json`, а по каждому компоненту `components/<компонент>/svace-dir.tar.gz`
и полный журнал сборки `build.log`. Чтобы проанализировать архив:
`tar -xzf svace-dir.tar.gz && svace analyze --svace-dir <проект>`.

Основные параметры: `--svace-option` (дополнительная опция `svace build`, можно повторять), `--build-cmd` и `--configure-cmd`
(свои команды сборки C/C++ вместо определённых автоматически), `--build-jobs`, `--timeout`.
Команда завершается с кодом 4, если хотя бы один выбранный компонент не собрался или не собрано ничего: так её удобно
использовать как проверку в CI.

## Безопасность

При фаззинге выполняется сторонний код: скрипты установки пакетов, системы сборки, сами компоненты.

- Запускайте только в Docker. Внутри контейнера весь недоверенный код работает от отдельного пользователя `fuzzer`
  без доступа к переменным окружения основного процесса, поэтому прочитать токен подписки он не может.
- У Claude Code отключены встроенные инструменты. Claude работает только через инструменты sbomfuzz (MCP):
  команды, запись файлов и сдача обёрток. Всё это выполняется в той же песочнице. Сам Claude Code запускается
  в закрытой папке и не читает настройки проекта, поэтому код компонента не может подсунуть ему хуки.
- Содержимое пакетов (README, исходники) может содержать попытки prompt injection. Claude прямо запрещено
  выполнять инструкции из этих файлов, но ограничения контейнера всё равно нужны.
- Ограничьте ресурсы контейнера, например `--cpus 4 --memory 8g`.

## Структура проекта

```
sbomfuzz/
  cli.py         команды: plan, generate, fuzz, report, run, svace, list
  svace.py       контролируемая сборка под Svace и архивация .svace-dir
  svace_report.py отчёт этапа Svace
  sbom.py        разбор CycloneDX JSON и purl
  fetch.py       загрузка компонентов (pip, Maven, архивы, git)
  claude_code.py запуск Claude Code (claude -p), который пишет обёртки
  mcp_server.py  MCP-сервер с инструментами для Claude Code
  tools.py       инструменты Claude и проверка сданных обёрток
  prompts.py     системный промпт и задание для Claude
  ecosystems.py  сборка, проверка и запуск Atheris / Jazzer / libFuzzer
  campaign.py    фаззинг одной обёртки: перезапуски, склейка повторов
  crashes.py     тип и сигнатура падения по выводу фаззера
  sandbox.py     запуск команд от непривилегированного пользователя
  stages.py      этапы конвейера: plan, generate, fuzz, report
  runner.py      команда run: все этапы фаззинга подряд
  gitlab.py      дочерний пайплайн GitLab CI по плану
  report.py      report.json и report.md
tests/           unit-тесты и интеграционные тесты с настоящими фаззерами
```

## Разработка

Тесты запускаются внутри образа (так же, как в CI):

```bash
docker run --rm -v "$PWD:/src" -w /src --entrypoint sh sbomfuzz -c "pip install -q pytest && pytest -v"
```
